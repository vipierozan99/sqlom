Why the absolute sqlite numbers moved, and why the ratios did not.

Re-running the sqlite suite after the connection-hoisting fairness fix produced
absolutes ~1.35x higher across EVERY contender -- including the rowform paths,
whose timed code that fix does not touch. Two candidate causes: the change, or
the machine. To distinguish them, the entire pre-change tree (library AND
harness, via git stash) was checked out and run again on the same box in the same
session. If the change were responsible, the pre-change tree would reproduce the
originally published numbers. It does not: it reproduces today's.

  command: python3 benchmarks/bench_sqlite.py --rows 200000 --limit 1000 \
               --iterations 300 --warmup 30 --repeat 3

  contender                     published    pre-change tree    post-fix
                              (earlier box)   (today's box)   (today's box)
  ------------------------------------------------------------------------
  rowform compiled (batch)         1.060 ms       1.389 ms        1.543 ms
  SQLAlchemy Core                4.252          5.196           5.240
  SQLAlchemy ORM                 6.647          9.127           9.132
  (means, median across trials)

So the machine this branch is measured on became ~1.35x slower between the two
runs -- ordinary for shared cloud CPU, and the reason absolute microseconds must
never be compared across sessions. Ratios are unaffected: the pre-change tree
gives 3.74x vs Core and 6.57x vs ORM today against 4.01x / 6.27x when published,
which is the ordinary run-to-run spread for these contenders (Core +/-14%, ORM
+/-27% -- see sqlite_setup_cost_ab.txt).

This is also why the fairness fix is quantified by the paired A/B in
sqlite_setup_cost_ab.txt rather than by differencing two suite runs: the effect
being measured (~8% on the Core ratio) is smaller than the noise between runs.
