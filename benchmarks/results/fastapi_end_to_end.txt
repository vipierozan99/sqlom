### FastAPI end-to-end, asyncpg, both libraries TUNED.
### uvicorn+uvloop+httptools on core 0, load generator core 1, Postgres cores 2,3.
### 100 rows/request, pool 10, 8 keep-alive connections.
### All endpoints verified byte-identical (7701 bytes) before every run.

A RE-RUN, after the query builder grew joins, aliases, grouping, set operations,
expressions, writes, transactions, CTEs, upserts and multi-table DML. None of
that touches this path — the benchmarked query's SQL is byte-identical and the
cached to_sql() is unchanged at ~196 ns — so the point is to check that claim
against the machine rather than assert it.

Two re-runs are shown, not one. A single median-of-3 cannot separate a real
change from this box's noise: the per-trial spread here is 4-15%, and the
published-vs-re-run gaps below are all smaller than that.

VERDICT: reproduced, with the ratios' precision stated honestly.

Only one of the three published ratios (5.42x vs /orm-default) falls inside its
re-run range. The other two sit just outside it, and in OPPOSITE directions:

  vs /core   published 2.73x, re-runs 2.60x and 2.68x  -> published is 2-5% HIGH
  vs /orm    published 4.80x, re-runs 4.98x and 5.07x  -> published is 4-6% LOW

Both gaps are smaller than the per-endpoint trial spread in this very table
(4-15%), so neither is evidence of anything having changed in the library — a
ratio built from two medians that each carry ~10% cannot be known to 3%. But
"inside the re-run range" would have been the wrong claim, and it is worth saying
so rather than rounding it to reproduced-and-done.

What the re-run does establish: /rowform is within 1-3% of its published rps
(2427 -> 2447, 2494), which is the number the new query-builder features could
plausibly have moved and did not. The ORM's ratio wandering upward is noise in
its tail, not a rowform gain: its p95 is 65-73 ms against a p50 of 11 ms.

So the published figures stay. Adopting 5.07x because it is the larger number
would be exactly the mistake METHODOLOGY correction 5 is about; conceding 2.60x
for /core on equally thin evidence would be the same mistake pointing the other
way.

SEE ALSO: core_idiom.txt
------------------------
Every "vs Core" figure in this file uses the `.mappings()` idiom that was later found
to charge Core for a per-key `str()` cast rowform never pays. Re-measured on the same
box with the positional idiom and byte-identical output, Core's throughput rises 42%
(psycopg: 582 -> 825 rps) to 49% (asyncpg: 914 -> 1359 rps), and the corrected ratios
are 1.57x (psycopg via FastAPI) and 1.79x (asyncpg via FastAPI). The tables above are
left as measured so the two idioms stay comparable. The ORM figures are unaffected.
